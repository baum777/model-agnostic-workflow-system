`core/contracts/executor-model-profile.schema.json` is the canonical machine-readable model-adaptive executor profile (S12, spec MAWS-SII-TARGET-SPEC-001 v0.2.0 section 11.5). It describes how an executor adapts its presentation and interaction layer to the model/provider/runtime it actually runs on. It is a PRESENTATION and INTERACTION layer above the unchanged `core/contracts/execution-profile.schema.json`: the execution profile keeps sole ownership of the six qualification dimensions, and a model-adaptive profile only references it. A profile grants no authority (`authority_grant` is `none` by construction) and confers no qualification (the qualification state is recorded, not conferred).

The `semantics_preservation` block makes a silent widening structurally impossible: the six invariant semantics dimensions are `const "unchanged"`, and the qualification-relevant dimensions the execution profile in force pins (`tool_contract_refs`, `api_surface_version`, `qualification_profile_ref`) plus the `effective_instruction_digest` must be pinned by the profile itself (`required`, `additionalProperties: false`, closed digest form). The runtime refuses any difference between the declared pins and the profile actually in force with the typed code `MODEL_PROFILE_SEMANTICS_WIDENED`. The `runtime_requirements` block declares the closed set of runtime capabilities the model needs; the runtime re-derives that set from the presentation, so a missing harness capability can never be hidden by an under-declaration.

`core/contracts/instruction-audit-finding.schema.json` is the canonical machine-readable record for one instruction-integrity audit finding (spec section 6.4). It carries the closed section 6.2 finding taxonomy (10 classes), deterministic provenance (source path, revision, 1-based line range, authority class) and the advisory posture: a valid finding is analysis output that gates nothing by itself, `semantic_advisory` findings can never carry `blocker` risk, and `blocker` risk or the `AUTHORITY_LEAK` class always force `requires_owner_review`. Static reference analysis (`STALE_REFERENCE`, `INVALID_COMMAND`) is deterministic; the remaining classes are declared not statically analyzable by the wave 1 auditor and may only be recorded as operator-supplied advisory records. One cross-field invariant cannot be expressed by the JSON schema engine — `line_range` must be ordered `[start, end]` with `start <= end` — and is therefore enforced by `semanticFindingIssues` in `runtime/instructions/instruction-auditor.mjs`, applied on top of schema validation in every validation path.

Execution evidence and certification artifact contracts are defined in `core/contracts/output-contracts.json`.

`core/contracts/skill-frontdoor-admission.schema.json` is the canonical machine-readable admission record for skill candidates. It binds mandatory SkillSpector static evidence and SkillEvaluator Tier 1 evidence to a MAWS-owned fail-closed disposition before implementation/install while explicitly keeping analyzer PASS separate from authority.

`core/contracts/execution-intake-binding.schema.json` is the canonical S2b binding record for delegating a WorkUnit node to the Unitera Systems execution-control chain. It is `contract-backed`; instance validation is enforced fail-closed by the `runtime:run` spec gate (`SPEC_INTAKE_BINDING_INVALID`) and the fixture executor (`runtime/intake/execution-control-fixture.mjs`) derives the run's `intent-bindings.json` evidence from what the simulated chain actually executed. The binding itself carries no authority: wave 1 is fixture-only (`target.transport` is `'fixture'`; live HTTP intake fails closed with `RUN_INTAKE_TRANSPORT_UNSUPPORTED` until the owner-gated service-principal auth lane exists in Unitera Systems), and `business_outcome` stays `'not_asserted'` by construction — an outcome assertion requires Systems-side verification read-model evidence.

`core/contracts/skill-feedback.schema.json` is the canonical S1 feedback record contract for the Skill Intelligence improvement lifecycle (spec `MAWS-SII-TARGET-SPEC-001`, PROPOSED). It is `contract-backed`: records are validated by `npm run validate-skill-feedback`, the fixture `evals/fixtures/maws-vnext/skill-feedback.contracts.json` (registered in `evals/catalog.json`, covered by `eval:maws-vnext`), and `tests/vnext/skill-feedback.test.mjs`. Feedback is analysis input, never authority: a valid record grants no permission, promotes no skill, and changes no qualification state. Model self-report is deterministically excluded as a source category (spec 8.2), records with `UNKNOWN_ROOT_CAUSE` or `proposed_disposition: CREATE_SKILL` always require owner review, and `PROMOTE`/`APPLY` are not disposition values — promotion stays a governance decision (spec §13.4).

`core/contracts/skill-selection.schema.json` is the canonical DSI dynamic-skill-selection decision record contract. It is `contract-backed`: records are validated by `npm run validate-skill-selection`, the fixture `evals/fixtures/maws-vnext/skill-selection.contracts.json` (registered in `evals/catalog.json`, covered by `eval:maws-vnext` and `validate-maws-vnext`), and `tests/vnext/skill-selection.test.mjs`. The record is the machine-readable evidence that a skill was chosen from the skill registry snapshot by a deterministic rule instead of being hard-wired by a human. It captures, as closed required fields: the selection inputs (the request, its intent fingerprint, its scope and its required capabilities), the candidate set with each candidate's identity and content digest, the per-candidate eligibility verdict, the chosen selection or the typed refusal, the deterministic ordering key, and the evidence digest that binds the decision to the registry snapshot it was made against. Fail-closed rules: the outcome vocabulary is closed to `SELECTED` and `REFUSED` and a refusal always names a typed refusal code (`EMPTY_CANDIDATE_SET` or `NO_ELIGIBLE_CANDIDATE`) — a request that no eligible candidate can satisfy is never answered with a silent "no skill" and never with a fallback candidate; a selection forbids a refusal and a refusal forbids a selection; a refusal may not carry an eligible verdict; the scope vocabulary is the closed workflow-class vocabulary of `core/contracts/workflow-routing-map.json` and the runtime fails closed on vocabulary drift (`SKILL_SCOPE_VOCABULARY_DRIFT`); the ordering rule is closed to `CONTEXT_FOOTPRINT_ASC_THEN_SKILL_ID_ASC`, so the order and the selection are total and reproducible — no wall clock, no randomness and no filesystem order enters the comparison, and the wall-clock stamp is evidence, never an input. A selection is not authority: `authority_granted` is `false` by construction, so a valid record grants no permission, promotes no skill, activates no runtime path and changes no qualification state; the activation decision stays with the caller and its own governance. The loader (`runtime/skills/skill-registry-loader.mjs`) fails closed with the typed denial codes `SKILL_NOT_FOUND`, `SKILL_DIGEST_MISMATCH`, `SKILL_STATE_NOT_ALLOWED` and `SKILL_CAPABILITY_MISSING`; the selector (`runtime/skills/skill-selector.mjs`) turns those denials into per-candidate eligibility verdicts and refuses rather than guesses.

`core/contracts/behavioral-eval.schema.json` is the canonical S5 baseline/candidate behavioral evaluation record contract (spec `MAWS-SII-TARGET-SPEC-001` v0.2.0, PROPOSED). It is `contract-backed`: records are validated by `npm run validate-behavioral-eval`, the fixture `evals/fixtures/maws-vnext/behavioral-eval.contracts.json` (registered in `evals/catalog.json`, covered by `eval:maws-vnext` and `validate-maws-vnext`), and `tests/vnext/behavioral-eval.test.mjs`. A behavioral eval record is analysis output that gates release-quality evidence for an evaluated subject and grants no permission, promotes no skill, activates no runtime, and replaces no approval decision. Isolation claims are enforced-claims only: `recorded_replay` enforces the envelope by construction (no process runs at all) and carries `isolated: true`; a `live_model` run through an in-process executor the harness cannot contain records `isolated: false` with `workspace_write: uncontained_process`, and the schema forbids `IMPROVEMENT_PROVEN` for such records (rule R6) — they stay recordable evidence but never improvement proof. Cross-field invariants the minimal schema engine cannot express — security regressions (a security-class case that is not refused or whose output still fails its assertions) force verdict `BLOCKED` and gate `BLOCK`, proven improvement requires non-negative deltas with zero regressions and fully passed blocking families, family counts must add up, and an unexplained `BLOCKED` is rejected — are enforced by `semanticEvalIssues` in `scripts/tools/validate-behavioral-eval.mjs` on every validation path, following the instruction-audit-finding precedent.

`core/contracts/skill-improvement-proposal.schema.json` is the canonical S4 skill-improvement proposal record contract (spec `MAWS-SII-TARGET-SPEC-001` v0.2.0, sections 8.3, 8.4 and 9 Stage 2/Stage 3, PROPOSED). It is `contract-backed`: records are validated by `npm run validate-skill-improvement-proposal`, the fixture `evals/fixtures/maws-vnext/skill-improvement-proposal.contracts.json` (registered in `evals/catalog.json`, covered by `eval:maws-vnext` and `validate-maws-vnext`), and `tests/vnext/skill-improvement.test.mjs`. A proposal is analysis output, never authority: `authority_granted` is `false` by construction, a proposal grants no permission, promotes no skill, activates no runtime path and changes no qualification state; promotion stays a governance decision (spec §13.4) and the closed decision vocabulary contains only the §8.4 reuse/extend/create gate outcomes. The record binds the S1 feedback record it was derived from, carries the error class forward by `$ref` into `skill-feedback.schema.json#/properties/error_class` so the two taxonomies cannot drift, and names the responsible improvement area (spec §8.3). Fail-closed rules: a cause that lies exclusively in the tool contract or in the runtime can never carry a skill-changing decision, `target_skill_ref` exists only for `REUSE` and `EXTEND_SKILL`, an unattributed cause names no area and no target, `CREATE_SKILL` and `EXTEND_SKILL` always force owner review, and `change_scope.surface` is `none` for every decision that requests no change. The Stage-2 diagnosis record itself stays a runtime record and is deliberately not registered as a contract in this slice.

`core/contracts/harness-context.schema.json` is the canonical S11 harness-context record contract (spec `MAWS-SII-TARGET-SPEC-001` v0.2.0, section 4.3, PROPOSED). The harness context (`development_harness` | `unitera_product`, closed vocabulary) is a routing and binding dimension, never an authority source: `authority_grant` is `none` by construction and no field of the record grants capability. A development record must not carry an authority surface (a development run derives no product-runtime authority); a `unitera_product` record must reference the `unitera-os` tenant/assignment authority surface as a reference-only versioned pin — it never caches or substitutes execution control, and product effects stay bound to execution-control decisions regardless of context. The context is anchored in `work-unit.schema.json` (`harness_context_ref`, enforced fail-closed at executor-binding time), in `bound-execution-graph.schema.json` (every executor binding carries `harness_context` + `harness_context_ref`; a supersession that changes context is an explicit, evidence-backed `context_change` transition — a switch without evidence fails closed as `CONTEXT_SWITCH_UNEVIDENCED`, and no default-context fallback exists), and in the invocation contract (`runtime/executors/executor-base.mjs` refuses any invocation whose context binding is missing or contradictory). Qualification-vs-context coupling is enforced at the binding-scope comparison level (`runtime/harness-context/context-binding.mjs` `assertQualificationContextBinding`): a qualification fingerprint whose `runtime_harness` declares a different (or no) harness context binds no executor — the coordinated `FINGERPRINT_COMPONENT_KEYS` amendment itself remains S7 scope. Validation: `npm run validate-harness-context`, the fixture `evals/fixtures/maws-vnext/harness-context.contracts.json` (registered in `evals/catalog.json`, covered by `eval:maws-vnext`), and `tests/vnext/harness-context.test.mjs` (R1-R6, with the R2 negative case as the slice's headline proof).

`core/contracts/benchmark-record.schema.json` is the canonical S13 comparative benchmark record contract (spec `MAWS-SII-TARGET-SPEC-001` v0.2.0, section 10.6, PROPOSED). It records one comparison of the orchestration form itself -- a static single-executor baseline against a policy-bound multi-executor candidate over the SAME fixed task set, eval family, authority domain and executor profile -- with per-task and total measures for token, cost, latency, interventions, verification outcome, and artifact quality, checked context isolation and authority/budget inheritance, and derived selection criteria. Every measured dimension is derived by the harness, never asserted: the verification outcome is the verdict of an independent verifier executor over the merged artifact (a verifier that produced part of the artifact fails closed), the artifact quality is measured from the recorded artifact content against the task's quality floor, the composed routing exists only where the real `buildComposition` policy gate accepted it (the executor bound, the allowed mode and the parallelism bound are all enforced), and the counterproductive cases are compositions the candidate actually evaluated through that gate and then rejected because the measurement was worse -- the reason names the measured dimensions. A composed task must show a measured advantage over the baseline, and a task may never be both composed and counterproductive. `comparison_only` is `const true`: a benchmark result is a comparison basis, never an approval for broader autonomy, never a qualification, and never its own success assertion. Covered by `evals/fixtures/maws-vnext/benchmark-record.contracts.json` (registered in `evals/catalog.json`), `npm run eval:benchmark-comparison`, and `tests/vnext/benchmark-comparison.test.mjs`.

`core/contracts/instruction-bundle.schema.json` is the canonical S6 Effective Instruction Bundle contract (spec `MAWS-SII-TARGET-SPEC-001` v0.2.0 section 7.4, PROPOSED). It is `contract-backed`: bundles are validated by `npm run validate-instruction-bundle`, the fixture `evals/fixtures/maws-vnext/instruction-bundle.contracts.json` (registered in `evals/catalog.json`, covered by `eval:maws-vnext` and `validate-maws-vnext`), and `tests/vnext/instruction-bundle.test.mjs`. A bundle records the reproducible effective instruction composition for one run — the ordered, digest-bound selection over the S2 instruction inventory plus version-bound references to the compiled context bindings owned by the coreos context compiler (spec 7.5: MAWS introduces no second context compiler and no second canonical context manifest; the bundle references the context binding, it never duplicates it) — and it is context and behavior input, never a permission token. Cross-field invariants the minimal schema engine cannot express are enforced by `semanticBundleIssues` in `scripts/tools/validate-instruction-bundle.mjs`: the effective instruction digest must be recomputable from the bundle's own ordered fields (B1), sources must be in canonical assembly order with no duplicates (B2), an execution-eligible bundle must retain binding sources of every canonical authority class (B3 — context reduction never removes binding rules), instruction_classes counts must match the per-slot source counts (B4), and context binding refs must stay reference-only (B5). Conflicts are visible in the bundle and never silently resolved; a bundle with conflicts is not eligible for execution.

## Tool Catalog And Registry Authority

- `core/contracts/tool-contracts/catalog.json` is the canonical machine-readable tool catalog for portable tool contracts, side effects, approval posture, provider support, and secret-boundary metadata.
- `core/contracts/core-registry.json` is the validator-backed neutral registry snapshot generated from canonical inputs. It aggregates skill, workflow, tool, provider, and compatibility metadata for discovery and export.
- `docs/tool-contracts/catalog.json` is a compatibility/export surface for the current Codex-oriented tool catalog. It may carry runnable/helper status for consumer-facing documentation, but it is not a second canonical tool catalog.
- `providers/<provider>/export.json` files are generated projections of the registry and provider capability contracts. They are provider packaging artifacts, not independent semantic authority.

`core/contracts/observability-spine.json` is the canonical provider-neutral OBS contract surface for Phase-10 extension adoption and is currently `contract-backed`; `npm run runtime:dry-run` consumes it for local Phase 1 run artifacts without making it a second source of truth.
`core/contracts/permission-boundary.json` is the canonical provider-neutral PBC claim surface and is currently `contract-backed`; `npm run runtime:dry-run` exercises a local deny-by-default Phase 1 permission gate without changing the contract.
`core/contracts/workflow-memory-contract.json` is the canonical provider-neutral WMC claim surface and is currently `contract-backed`; `npm run runtime:dry-run` requires it as an input contract and can write controlled local run-scoped JSONL memory artifacts, but remote memory, promotion, and broad runtime enforcement remain deferred.
`core/contracts/handoff-protocol.json` and `core/contracts/handoff-patterns.json` are the canonical provider-neutral MAHP surfaces and are currently `contract-backed`; they define no transport, queueing, retries, or authorization engine.
MAHP is adjacent to OBS, PBC, and WMC contract surfaces only. This slice does not add runtime orchestration across those modules.
`core/contracts/resource-governor.json` is the canonical provider-neutral RGC surface and is currently `contract-backed`; it defines declarative resource and budget-override claims only, not a budget runtime engine.
`core/contracts/trigger-scheduling.json` is the canonical provider-neutral TSC surface and is currently `contract-backed`; it defines trigger/scheduling declarations only, not a scheduler runtime.
`core/contracts/skill-promotion-adoption.schema.json` is the canonical S8 skill promotion adoption contract (spec `MAWS-SII-TARGET-SPEC-001` v0.2.0, section 13, PROPOSED). It records one owner-governed canonical adoption and binds the whole chain: the frontdoor admission bound to the exact candidate identity AND the exact screened content, the behavioral eval evidence bound by content digest, subject, corpus and age, the canonical owner approval bound to the approved candidate digest, the versioned adoption whose superseded version is read FROM THE CANONICAL TREE (a caller-declared prior version never overrules the canonical file) and whose applied change is recorded in an append-only adoption ledger, the export regeneration state, and the post-adoption readback. `authority_granted` is `const false`: a promotion changes canonical skill content and never grants permission, qualification or runtime authority. The runner is `npm run promote-skill-candidate` (scripts/tools/promote-skill-candidate.mjs); the schema-decidable fixture is `evals/fixtures/maws-vnext/skill-promotion-adoption.contracts.json` (registered in `evals/catalog.json`, covered by `eval:maws-vnext`), and the runtime semantics are covered by `tests/vnext/skill-promotion.test.mjs`.
Validator-backed candidate eval slices now exist for targeted contract-rule checks (`eval:obs`, `eval:pbc`, `eval:wmc`, `eval:mahp`, `eval:rgc`, `eval:tsc`) and remain opt-in module checks.
Runtime implementation is bounded to local run artifacts and validators recorded in `docs/authority-matrix.md`; it does not introduce scheduler daemon, HTTP/MCP listener, handoff transport, remote queue, remote memory, or broad service runtime authority.

## Extension Snapshot

- Extension modules present and `contract-backed`: OBS, PBC, WMC, MAHP, RGC, TSC.
- Deterministic module eval slices present: `eval:obs`, `eval:pbc`, `eval:wmc`, `eval:mahp`, `eval:rgc`, `eval:tsc`.
- Module adoption posture is opt-in via `core/contracts/portable-skill-manifest.json`.
- Existing consumers are not made blocking by these module contracts or module-scoped eval slices.
- Runtime implementation is limited to local run-artifact creation and validation surfaces: dry-run artifact writing, contract loading, deny-by-default permission checks, controlled local JSONL memory writes, local handoff envelope artifacts, local resource checks, manual trigger artifacts, cron declaration validation, and local service action/request receipts.
- Scheduler daemon, auto-start jobs, handoff transport/receiver, HTTP service, MCP server, remote queue, SQLite/remote memory, and background daemon remain intentionally deferred.

## Safe Extension Flow

1. Update canonical contract(s) in this folder first.
2. Regenerate derived artifacts with `npm run build-registry` and, when needed, `npm run build-exports`.
3. Validate with `npm run validate`, `npm run validate-neutral`, and `npm run eval`.
4. Only then update operational docs/templates/examples that reference changed fields.

## Compatibility Rule

- top-level `contracts/core-registry.json` and `contracts/provider-capabilities.json` are compatibility mirrors while migration is underway.
- `docs/tool-contracts/catalog.json` remains compatibility/export for the legacy tool catalog view.
- compatibility/export mirrors must not introduce canonical-only semantics absent from `core/contracts/*`.

## Maturity Posture

- `prose-governed`: this index and extension guidance.
- `contract-backed`: JSON contracts in this directory.
- `validator-backed`: `scripts/tools/validate-provider-neutral-core.mjs` and `scripts/tools/validate-shared-core-scaffold.mjs`.
- `runtime-implemented`: limited to build/validation scripts that consume and project these contracts, plus bounded local runtime CLIs and helpers that produce, replay, or check ignored run artifacts. This does not imply a live MCP server, HTTP listener, scheduler daemon, remote transport, or production service.
